A request waits for you when a rule holds it, when the agent reaches a host the profile does not name, when it asks to write a path, or when Claude Code asks for a permission. You answer it in one of three places, and every answer goes to the same queue.

## What a request shows

<RequestExample
  profile="infra"
  hue="p1"
  session="p71a"
  cwd="~/Development/infra"
  kind="tool"
  summary="Run a command"
  timer="39s"
  fill="65%"
  status="The agent is waiting for your answer, 39s left."
  note="Apply staging"
  details="acme up --stack staging --yes"
  scope="tool claude Bash acme up"
/>

The summary and the scope come from doriath. Text the agent wrote, such as a command's description or the reason for a write, sits beside a curled rule and says which agent wrote it. For a tool request, the details are the agent's too.

The time is how long the agent keeps waiting. After that the request is parked: the agent got an error and moved on, and allowing still lets its next try through. A parked request stays answerable until the session ends.

## The answers

- Allow once lets this request through. Later identical requests ask again.
- Allow for this session lets this request and identical ones through until the session ends. "Identical" is the request's scope, shown as "An allow covers".
- Deny refuses it. The agent gets an error that says so.

A host and a writable path offer no "once": once reached or written, they stay reachable, so those last for the session. To keep an allow for later sessions, add the profile lines the request shows. doriath never edits profiles itself, because a profile may come from nix.

## Desktop notifications

With `[approvals] desktop = true` in `config.toml`, which is the default, each request is a notification with its answers as buttons. It holds the request for `host_wait`, two minutes by default, while you decide.

## The approvals page

```sh
doriath approvals web --open
```

The page lists the requests of every running session, and the last day's answers from the audit log. It serves on `127.0.0.1:7341` and prints a link with a token: the browser keeps the token in a cookie for 30 days, so other users of the machine and other sites cannot read or answer requests. The page loads nothing from the network.

Run the command again while the page serves, and it prints the link again, once the page proves it holds your token. With home-manager, `programs.doriath.approvals.web.enable = true` runs the page as a systemd user service, and `doriath approvals web --open` opens it.

## The terminal

```sh
doriath approvals
doriath approvals allow ID --for session
doriath approvals deny ID --reason "use the staging stack"
doriath approvals watch
```

`allow --for` takes `once`, `session` or a duration such as `30m`. `watch` asks about each new request in turn.

## On a remote host

When doriath runs on a server, keep the page on the server's loopback address and reach it through SSH, so no port opens to the network:

```sh
ssh -L 7341:127.0.0.1:7341 server
doriath approvals web
```

Open the link it prints in the browser on your own machine. Any local port works, such as `-L 8000:127.0.0.1:7341` with `8000` in the link. Without a tunnel, `doriath approvals watch` in a terminal on the server answers the same requests.

<Aside type="note">
  The page accepts only loopback names in the Host header, so a site that
  resolves its own name to 127.0.0.1 cannot reach it from your browser.
</Aside>

## Writable paths

In the jail, `doriath request write PATH --reason TEXT` asks to make a path writable, and `doriath request wait ID` waits for the answer. The agent can ask only for a path it already sees. doriath refuses, before asking, paths such as `.git`, `.ssh` and its own configuration.

On the host, `doriath grant write PATH` makes a path writable in the running session directly, and can also attach a directory the jail does not see.
