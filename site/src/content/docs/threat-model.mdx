## Assumptions

doriath assumes an agent that acts against your intent, after a prompt injection or a mistake. The agent runs each program that the jail shows, writes each file that it can write, and tries all that the kernel allows. [Architecture](/architecture/) describes the parts behind each guard.

You trust these parts:

- The kernel, bubblewrap and doriath's own code. Nobody has audited doriath.
- The author of each profile and module that you use.
- The forge and the cloud, which apply the permissions of your tokens.

Other programs of your user and other local users are outside the model. Where one of them gains something from a session, [limits](#limits) says so.

## Protected things

doriath protects these things from the agent:

- Files outside the paths that the profile names, such as your home directory and other projects.
- Tokens and keys. The agent uses them through the proxy and never reads them.
- The network: your local network, and each host that the profile does not name.
- Actions on a forge or a cloud that you did not approve, such as a merge or a release.
- Code that your machine runs from the checkout on its own, such as git hooks and `.envrc`.
- Your answers. Only you approve a request.

## Profiles

Without doriath, an agent can do all that you can do. A profile replaces that with a list of grants that you can read. The safety of a session thus depends on its profile, and most profiles combine the [shipped modules](/reference/modules/).

Two kinds of grant let the agent act outside the jail:

- A writable path that your machine runs later, such as shell startup files, `~/.local/bin`, git hooks or `.envrc`. At your next login or commit, code that the agent wrote runs as you, outside the jail.
- A rule that allows every request with a credential of broad scope. The proxy keeps the token, and the agent can still send any request that the token permits.

A profile without these grants still keeps `~/.ssh`, keyrings, other repositories and raw tokens out of the jail, also if it allows many hosts and paths.

A profile can also turn guards off. The [`[hardening]`](/reference/configuration/#profile-keys) keys allow namespaces or `ptrace`, or remove Landlock. doriath shows these keys when it asks about the profile.

A [repository profile](/reference/configuration/#repository-profiles) comes from the repository, where an agent can write it in one session for the next. doriath asks you before the first session of each profile in each repository, and again when a profile gives more than you allowed. The question lists each grant. A repository profile cannot do these things:

- Mount your keys, logins, git and jj config, or doriath's own directories.
- Add a forward, a port on your machine, or a `[code]` entry.
- Add rules for a host that your profiles or modules already define.

A profile can change without your edit, such as a module after an upgrade. Read the lines that doriath shows before you answer.

## Limits

These limits stay open with a profile that has neither grant from [profiles](#profiles). They are in groups by what the agent gains. Each group ends with the steps that make it smaller.

### Data that leaves

#### Allowed hosts

Each allowed host can receive data, because work needs writes. The shipped modules allow dozens of hosts.

- The agent can send its own credential to an allowed host. The `claude` module refuses requests to api.anthropic.com with an `x-api-key` header. A sign-in token of another account passes, and that account then receives the data.
- The `github` module lets `gh` post comments. doriath cannot hold comments outside your repositories, because GraphQL names a repository by an opaque ID.
- A comment or a label in your own repository can start a bot or a workflow that acts with more rights than the agent. The `gitlab` module holds a note that has a quick action, such as `/merge`.
- For a host without an `[[http]]` entry, doriath checks only the host and the TLS server name. Behind a CDN, a request can name any site on that CDN. Encrypted Client Hello can hide the server name.
- A rule matches the path that the proxy reads. A server that decodes a path again and splits it at another place can read a different path.
- A host that the profile names exactly can resolve to a private address, and the agent then reaches that address.

doriath holds each push for your approval, but it does not limit which branches a push changes. Set rules such as no force push to `main` in the branch protection of the forge.

#### Cloud credentials

The credentials of the [`aws` module](/guides/cloud/) never enter the jail, but the agent can use them through the proxy within the rules. The rules let reads pass, hold other calls, and refuse calls that return credentials.

A read that returns other secrets reaches the agent if a rule allows it. Examples are a database password in a stack output and the environment of a function. An allowed read can also carry data out, such as a request to a bucket that someone else owns. The rules know a read by its name, which starts with `Describe`, `Get` or `List`.

#### System paths

The agent can read each world-readable file in `/etc`, `/nix/store`, `/usr`, `/sys` and other system paths, also secrets in the Nix store. A read allowlist would break the host toolchain, which reads many paths.

doriath hides `/home`, `/root`, `/run`, `/tmp`, `/var` and other roots that it knows. A top-level directory that it does not know, such as a data disk at `/data`, stays readable.

Some system files name things outside the jail. `/proc/self/mountinfo` lists the mounts of your machine, and the garbage collector roots of Nix name the paths of your other projects.

To make this group smaller, mount only the project, allow only the hosts that the task needs, and keep secrets out of world-readable paths. Give the cloud command a role for this work only.

### Tokens for named programs

#### Allowed programs

Credentials and `[[egress.programs]]` hosts go only to named programs. A bare name matches only a program under a system path that the agent cannot write, such as `/nix/store`. With the `nix-daemon` module, the agent can add paths to the Nix store, so a bare name matches only the store paths that exist when the session starts.

When the session starts, doriath pins each program that `binaries` names, with the files in its folder. It also pins the library folders in the program's ELF `RUNPATH`, such as `$ORIGIN/../lib` in a JDK, if they stay inside the folder above the program. A program gets nothing in these cases:

- It runs another file at that path, or the same file after a change.
- It runs code from a file outside the system paths that doriath did not pin. This includes `LD_PRELOAD`, libraries that it loads later, and programs that the session builds.

A profile can name archives in `[code] archives`, such as the `A-server.jar` of a Bazel install base. When the session starts, doriath reads each archive and records the executable pages of every native library in it. A program that unpacks such a library into a temporary folder, as Bazel and netty do, keeps its credential.

doriath compares the pages that the process maps with the recorded pages, because the program deletes the file after it loads it. A library that no archive ships still gets nothing. The check needs `/proc/PID/mem`, so it fails closed where `kernel.yama.ptrace_scope` is 2 or higher.

The agent can still do these things:

- Run a named program with any arguments, or control it through writable config, such as `~/.config/gh`.
- Give a TCP socket to a named program after another program writes the request. doriath names the program when the connection opens.
- Make a named program load any library that an archive in `[code] archives` ships. These are libraries that you already trust. doriath compares only the executable pages, so a copy with the same code and other data pages also passes.
- Put its own program at a writable path that `binaries` names. The program gets nothing in that session. The next session pins the file that it finds there and gives it the credential. doriath warns about each such path at session start.

Request rules and approvals decide what named programs can do. To make this group smaller, name programs by a path that the agent cannot write, and give each token the smallest scope that the forge offers.

### Code that runs outside the jail

#### Writable repositories

With `vcs-readwrite` or `vcs-readonly`, the agent creates, moves and deletes branches and adds worktrees. At the end, doriath repairs the store and its submodules, as [guarded actions](#guarded-actions) describes. `doriath restore` covers branches, tags and the newest stash entry. It does not cover other refs, such as remote-tracking branches and notes.

If doriath stops before the end of a session, for example because it was killed, the repositories keep what the agent wrote: unchecked objects, worktree pointers and a rebase to continue. doriath does the end step when the next session uses the repository, or at `doriath clean`. Each other session that starts names the sessions that wait. Until then, git on your machine reads what the agent left.

##### Agent worktrees

git on your machine follows the `.git` file and admin directory of an agent worktree. Thus `git status` there can run hooks that the agent wrote. doriath resets these files in milliseconds, again at the end, and reports each change. doriath only reports a worktree that claims a path outside the writable mounts, or that reaches outside them through a symlink.

Review the files of an agent worktree as you review a pull request. A copy of the repository for each session would cost disk, time and a step to land the work.

##### Nested repositories

git on your machine follows the config and hooks of a `.git` directory that the agent creates elsewhere in a write mount, when you run git in that folder. If the index names such a folder as a submodule, git also reads it from the root of your checkout. doriath thus moves aside each nested repository that the index names and that is new or changed, in less than a second and again at the end. A `git submodule add` by the agent is moved aside in the same way, and the end report names it.

##### Files that tools run

In the session's repository, and in a repository where the agent uses a module after [`doriath request module`](/reference/commands/#doriath-request-module), the [modules in every profile](/reference/modules/#modules-in-every-profile) keep the files of known tools read-only. They cover three triggers: git events, entering the folder and opening the editor. `vcs-readwrite` also keeps the files of mise and agents. doriath also holds the folder that `core.hooksPath` names, if it finds the key when the session starts.

These cases stay open:

- A tool that no module lists, or a checkout that you mount writable yourself, leaves such files writable.
- The holds cover the root of the repository. An `.envrc` in a folder below the root stays writable.
- A held file can name a script, such as a hook command in agent settings. The script stays writable.
- Where a held file is missing, doriath moves out what the agent creates there, through inotify. Between the creation and the move, a tool on your machine can read the file. Without inotify, doriath moves it only at the start and the end of the session.
- The agent can create a missing file that no module holds. mise asks you before it runs a new file. A tool that does not ask runs it.
- A guarded file that is a symlink in a writable checkout, such as a `.pre-commit-config.yaml` from git-hooks.nix, cannot be mounted read-only. doriath puts the link back in milliseconds when the jail changes it. A git command that you run on your machine in that moment can read the agent's version.
- A jj workspace config with content, in the place that older versions of jj used, stays where it is. doriath warns about it at session start.

##### Store state

- The agent can write a `commondir` into a store whose root it can write. This sends git on your machine to another repository. doriath removes the file in milliseconds, and again at the end.
- While the session runs, a rebase or cherry-pick that the agent left in a store can hold `exec` lines. git on your machine runs them if you continue it. doriath moves this state aside only at the end.
- The agent can change what your index stages and which branch `HEAD` names. Neither runs code.

##### Edits to guarded files

`doriath request edit` changes a guarded file without a question when each change is on the profile's safe list. You trust that list: a module that marks a setting as safe lets the agent change it in your repository. `vcs-readwrite` lists only upstream tracking, and refuses a remote's URL as a branch's remote.

#### Containers

The broker checks the name of an image. The agent can build an image, or give an allowed name to another image, so the name does not say what the image holds. A container gets no more than the agent has. doriath does not check or pin the base images that a build pulls in podman.

The broker checks the mounts of a container when the agent creates it and again when it starts. Between the last check and the mount, the agent can swap a directory above a mount source for a symlink.

#### Paths that return to the host

These paths let you resume sessions, read output, reuse build caches and add paths without a restart. Each one carries data from the jail back to you.

- Claude's transcripts return to `~/.claude/projects`. A session that you resume outside the jail reads history that the agent wrote.
- The agent reads the project's earlier transcripts, also text that you pasted into a session outside the jail.
- One session can plant files in caches and container storage that later sessions of the same profile trust. This includes a program at a writable path that `binaries` names, which the next session pins with its credential.
- doriath cannot know each path that your machine runs files from. It refuses requests for your keys and logins, and warns on the paths that it knows, such as `~/.local/bin`, `~/.config/systemd` and `/tmp`. A request for another such path asks you without a warning, and code that the agent writes there after your allow runs outside the jail.
- A write or read request that you allow can attach a directory that the jail does not show, and the agent can then read it. The grant lasts until the session ends, because an open file stays open after doriath removes a mount. The helper that applies each grant has full capabilities over the mounts. It runs doriath's own read-only binary and never follows symlinks.
- Builds of the `nix-daemon` module run outside the jail, without the allowlist.

#### Your browser and terminal

- A link that the agent opens runs in your browser, where you are signed in. Its site receives the whole link, and a page that acts on a GET request acts as you. doriath opens a link without a question only where a rule allows its host and path, such as an agent's sign-in page or the forge that the profile already reaches. Sign-in, account, settings and app pages of a forge ask you first.
- With Chrome open, the `claude` module lets Claude drive your browser through the Claude in Chrome extension. The browser runs outside the jail, with your sign-ins, and its requests do not go through the proxy. Only JavaScript and file uploads ask you first.
- Escape sequences in agent output can change the title or state of your terminal, and can set the clipboard of your terminal. The terminal bar drops requests to read the clipboard. With [`bar = false`](/reference/configuration/#configtoml-keys) they reach your terminal, and some terminals answer with the clipboard contents.

#### Ports

- A sign-in forward lets programs on your machine reach one port in the jail for five minutes.
- A forward that you allow, with `doriath request forward` or a link to `localhost`, lets each local user of your machine reach that port in the jail until the session ends. A [`[[forward]]`](/reference/configuration/#forwards) in your profile does the same in each session, without a question. A program on your machine that expects its own server on that port reaches the jail instead, for example when that server is not running.
- `doriath forward` listens on the host's loopback address, which every local user can reach, also on a shared server.
- A connect that you allow, with `doriath request connect`, lets the agent reach one TCP port on the loopback address of your machine until the session ends. The service there sees a local client and may trust it as it trusts your own programs, such as a database tunnel that is already signed in or a debugger. The same holds for the ports in `egress.tcp_ports`.

To make this group smaller, use `vcs-readonly` where the task permits, review the end report of each session, and allow a forward or a connect only for the port that the task needs.

### Your answers

The agent cannot answer a request, but it writes part of what you read before you answer.

- Tool requests carry text that the agent wrote, and the notification says so. Many requests in a row make a click on allow likely. Thus doriath refuses new requests while 32 wait. It shows 10 other notifications at once, then one each minute.
- The session description comes from the agent, through `doriath describe`. doriath shows it in quotes, marked as the agent's text, and never in a notification title. The agent can write a description that does not match its task.
- doriath removes control, invisible and direction characters from the agent's text. It does not find a letter that looks like another letter, in a host name or a path.
- An allow for the session covers each later request with the same scope. For a host, the scope is the host. For a command or a tool, it is the exact text or input.
- With the `clipboard` module, an allowed read gives the agent the image that you copied last, whatever it shows. An allow for the session covers every later read, also reads that you did not start with a paste.
- Claude's Remote Control lets each person signed in to the profile's claude.ai account control the session and answer Claude's permission prompts. The jail and the proxy rules still apply.
- A browser sends the cookie of the approvals page to each server on `127.0.0.1`, also to a port that you forward from the jail. The agent can then hold the cookie. It still cannot reach the page, because doriath refuses a forward or a connect to the page's port.
- The dialog for a keyring secret opens only when a session starts, or after you click **Try again** on the card of the secret. The agent cannot open it.

To make this group smaller, read the facts of a request before its text, and allow for the session only what you expect to repeat.

### Shared kernel and user

The jail runs as your UID on the host kernel. A kernel or bubblewrap bug lets the agent escape as your user. Only a virtual machine isolates more.

- seccomp allows netlink beyond routing, nested seccomp filters and `memfd_create`, because Chromium, .NET and `ss` need them. Code in memory gives the agent nothing new, because a file that it writes can also run.
- The podman service runs as root in a subordinate user namespace, without its own seccomp filter. An escape from the container runtime gets that access. The agent reaches only the broker.
- The agent can send signals to doriath's init, which is non-dumpable. A kill ends the session. A stop holds new proxy connections, so the agent chooses when doriath names the program behind each one.
- A program that `doriath exec` starts joins the jail a moment before its seccomp filter applies. Where `kernel.yama.ptrace_scope` is 0, the agent can try to write to the memory of that program in this moment.
- Sessions have task and memory limits where `systemd-run --user` works, but no CPU quota by default. `[limits] cpu` sets one. Without `systemd-run`, doriath warns and the session has no limits.

If a kernel exploit is your main threat, run doriath in a VM, or use a microVM tool with its coarser rules.

### Configuration that you trust

- `doriath run --learn` reaches every public host for that session. Use it only for builds that you start, and never give it to an agent.
- A secret given as a command runs on the host with your environment. You trust the author of the profile. The program in `SSH_ASKPASS` also runs on the host with your environment.
- Claude's login stays in the keyring, and the jail has only a placeholder. A `.credentials.json` that Claude wrote earlier in the cache of a profile is deleted at session start. The proxy adds the login for the `claude` program on `api.anthropic.com` and `claude.ai`, so the agent can use the login within the rules of those hosts, as with any credential.
- OAuth logins, with their refresh tokens, and keyring secrets stay in the keyring of your desktop. Other programs of your user can read them from an unlocked keyring outside the jail.

## Other sandboxes

doriath shares your kernel, and nobody has audited its code. Its profiles set what each project can reach, and requests wait for your answer. Each cell gives the default or documented setup of the tool, as the public documentation in the Sources list below described it in October 2026. The other tools may have changed since then. A cell that says "not documented" means the author did not find the answer in those pages, not that the tool lacks the feature.
